# Installer and portable copy

This page is for people who build Vox's installer or deploy it. To install Vox, see
[Installing Vox](install.md).

`installer/Vox.Installer` is a WiX Toolset v5 project that builds `Vox.msi`. It installs per machine
to `C:\Program Files\Vox`, the secure location Windows requires before it grants UI access
([signing.md](signing.md)), and adds:

- every file of a published Vox: `Vox.App`, `Vox.Watchdog` and `Vox.Service`, self-contained, so no
  .NET runtime has to be installed first, with the sounds, keymaps and the user guide;
- the `VoxService` Windows service (LocalSystem, automatic start), which reads the sign-in, lock
  and UAC screens;
- a Start menu and a desktop shortcut to `Vox.Watchdog.exe` (which starts Vox and restarts it after
  a crash; after repeated crashes it starts Narrator, or the screen reader trial mode stopped, instead). The Start menu shortcut has the hotkey **Ctrl+Alt+V**, so Vox can be started without
  seeing the screen;
- with `STARTATLOGON=1`, a shortcut in the all-users Startup folder, so Vox starts at every sign-in.

The setup dialog is WiX's minimal UI: the MIT licence with an "I accept" check box, Install, the
UAC prompt, then a last page with a **Start Vox now** check box (checked), so someone who installed
with Narrator or another screen reader hears Vox as soon as they press Finish. Every page is
standard Windows controls, readable with Narrator, NVDA or JAWS.

Uninstalling removes all of these and stops the service. Users' settings in `%APPDATA%\Vox` are
kept.

## Installer properties

| Property | Default | Effect |
| --- | --- | --- |
| `STARTATLOGON` | `0` | `1` starts Vox at every sign-in, for every user |
| `DESKTOPSHORTCUT` | `1` | `0` leaves out the desktop shortcut |
| `INSTALLSERVICE` | `1` | `0` leaves out the secure-screen service |
| `UPDATECHANNEL`, `KEYBOARDLAYOUT`, `MODIFIERKEY`, `VERBOSITY`, `SPEECHRATE`, `LANGUAGE` | empty | The computer's default settings ([enterprise.md](enterprise.md)) |

```powershell
msiexec /i Vox.msi                       # with the setup dialog
msiexec /i Vox.msi /qn STARTATLOGON=1    # silently, starting Vox at every sign-in
```

A silent install doesn't start Vox; it starts at the next sign-in (with `STARTATLOGON=1`) or with
Ctrl+Alt+V.

## The portable copy

`Vox-<version>-portable.zip` holds the same published files plus an empty `userConfig` folder.
Unzipped anywhere (a folder in Documents, a USB stick), `Vox.Watchdog.exe` starts it without
installing anything or needing administrator rights, and it keeps its settings and logs in
`userConfig` (`VoxPaths`). It has no UI access (it isn't under Program Files), no secure-screen
service and no Ctrl+Alt+V hotkey. A running Vox makes another portable copy from the Vox menu
(`PortableCopy`).

## Building

The installer builds only on Windows, so it isn't part of `Vox.sln`. Use the **Release** workflow
(Actions tab, Release, "Run workflow"): give a version, and tick **Publish a GitHub release** to
make a release with the MSI and the portable zip (a pre-release unless you untick that box).
Without it, both files are kept as the run's artifact. Locally:

```powershell
foreach ($p in 'src/Vox.App', 'src/Vox.Watchdog', 'src/Vox.Service') {
  dotnet publish $p -c Release -r win-x64 --self-contained true -o publish\Vox
}
dotnet build installer/Vox.Installer -c Release -p:PublishDir="$PWD\publish\Vox" -p:VoxVersion=1.0.0
```

`dotnet publish` of `Vox.App` copies `assets\` and `docs\guide\` into the publish folder
(`PublishVoxAssets` in `Vox.App.csproj`). The keyboard reference (`docs\guide\keyboard.html`) is
generated by running Vox.App; the workflow makes it with a framework-dependent build.

With the repository secrets `VOX_SIGNING_CERTIFICATE` (the .pfx, base64) and `VOX_SIGNING_PASSWORD`,
the workflow signs the three programs (so Vox gets UI access) and the MSI. Unsigned builds work, but
Windows SmartScreen warns about them on download and Vox can't read elevated windows.

The WiX project has only been checked on paper so far: WiX doesn't run on Linux, where it was
written, so the first Windows run of the Release workflow is its first real test.
